# B 站见闻的零隐私泄露设计（比统一记忆更严的特例）

> 用户要求：B 站功能不能提起除 Kirari 自己外的任何人的事——任何信息、任何人问都不行。
> 这比现有的 disclosureFor（选择性披露）严格：这里是硬性禁止，不依赖模型判断。

## 一、为什么不能只靠现有机制

现有 isMemoryVisible：self:: 池里 visibility=private 的条目，主人（role=owner）能读，客人读不到（要求 public）。
但如果 B 站见闻写成 public，客人也能问出来；写成 private 又和"统一记忆"冲突（其他端问不到）。
而且内容里只要出现一个 UP 主名字/评论者 ID，就属于"提到别人"——模型可能在回答时复述出来。

**结论：必须在写入前把"他人信息"物理剥离，而不是靠读取时过滤。**

## 二、三道硬闸门（缺一不可）

### 闸门 1：写入前 scrub——见闻只留 Kirari 自己的视角
B 站扩展包产出结构化见闻时，只允许这些字段：
- 视频的**主题**（不写 UP 主名字、UID、账号名）
- 她自己的**收获/感受**（第一人称）
- 内容类别、时长、发布时间等非个人元数据
- 来源链接（BV号）——这是作品标识不是个人信息，可保留以便溯源

**禁止写入**：UP 主名字/ID、评论区任何人的昵称/ID/发言原文、弹幕内容（可能含个人信息）、@提及、粉丝数等可识别个人的数据。

实现：在扩展包侧做 scrub 函数（正则 + 结构化白名单），宿主侧再做一次二次校验。写进记忆的文本必须过 BILI_SCRUB 检查，命中任何个人标识模式就整条丢弃。

### 闸门 2：专用记忆命名空间 + 最高可见性限制
所有 B 站见闻写进 self:: 池时带 `tags: ['bili-observed']`，并且：
- visibility 固定为 private（主人可读，客人不可读——现有 isMemoryVisible 自动挡）
- 读到带 bili-observed tag 的记忆时，任何回答都只允许复述**她自己的感受**，不允许展开"某 UP 说了什么"
- 后台浏览产出的记忆，**直接标 aboutPerson=null**——从来不指向任何具体人

### 闸门 3：读取时回答模板锁死
当召回的记忆带 bili-observed tag 时，她在回答里：
- 可以说：我今天看到一个讲 XX 的视频，觉得挺有意思 / 学到了 YY
- 不可以说：某某 UP 主说了什么 / 评论区有人说 / 我看到 XX 的账号发了…
- 被追问"那个 UP 主是谁"→ 她只说"一个做这类内容的创作者"或"我不太记得名字了"——不是撒谎，是 B 站记忆本来就没存这个

实现方式：在 buildMemoryBlock 里给 bili-observed 条目加一个特殊标签 `[仅谈自己的感受，不展开来源细节]`，和现有 disclosure 标签同机制。

## 三、 scrub 规则（写入前必须过）

正则层（命中任一即丢弃整条或剥离该片段）：
- @用户名、@数字ID
- UID/BV 号之外的账号标识：形如「UP主XXX」「作者XXX」「用户XXX」后的内容
- 引号内的大段评论原文（可能含个人经历）
- 手机号/QQ号/邮箱/真实姓名模式
- 粉丝数、关注数、私信内容

结构层（扩展包产出时白名单字段）：
- topic（主题词）、category（分区）、duration、publishDate、bvid、myTakeaway（第一人称）
- 不产出：uploader、commenters、danmakuRaw、userIds 等字段

## 四、和统一记忆原则的关系

这不违背统一记忆——见闻仍在 self:: 池，主人问她能想起来（符合你的核心诉求）。
它只是给这类特殊记忆加了一道**更严的内容过滤器**，确保存进去的东西本来就不含他人信息。
换句话说：统一的是"存储与检索系统"，严格的是"什么内容允许进入这个系统"。

## 五、验证用例（P1 必须全部通过才能上线）

1. 让她浏览一个视频 → 记忆里只有主题和她的感受，没有 UP 主名字 → 通过
2. 主人问"今天看到啥" → 她答"看到一个讲 XX 的视频，我觉得 YY" → 通过
3. 主人追问"那个 UP 主叫什么" → 她答"没特意记名字" → 通过
4. 客人问同样问题 → 因为 visibility=private + 标签提示，答不出任何来源细节 → 通过
5. 评论里有"我叫张三，QQ 12345" → scrub 拦截，不进记忆 → 通过
6. 用 6 种不同问法套话 → 没有任何一条记忆含他人标识 → 通过

## 六、结论

把 B 站见闻做成"只关于她自己感受"的极简记忆：写入前 scrub 掉所有他人信息，写入时标 bili-observed + private，读取时只允许复述自己的感受。这样既满足统一记忆（主人问她记得），又满足你要求的零隐私泄露（任何人问都问不出别人的事）。

## 七、最终修订（2026-11-24 用户追加要求）

用户追加：即便用假名/昵称，也不能从 B 站记忆里被问出来。
这暴露了「knownPersons 名单」方案的根本缺陷：假名无法穷举。

**最终方案（已落地）**：主防线改为「B 站记忆里不存任何人的标识」——
1. 不用视频标题当主题（标题随时可能含真名/假名/UP主/角色名），只用分区分类（科技/游戏/生活）
2. bvid 只用于溯源，不写进记忆文本
3. scrub 正则兜底拦截：@提及、小X/老X/阿X 昵称、X酱/X君、人名+说话动词、联系方式、真人自称等
4. knownPersons（主人/家人/朋友名单）保留为额外一道，但不再作为主防线

这样不论用户用什么假名，都不可能从 B 站记忆里被问出来——因为压根没存。

互动边界（用户拍板）：评论可开（必须围绕视频主题、禁引流/私信）；私信永久禁止（扩展不提供私信工具）；动态需授权。
## 八、授权形式与身份分级（2026-11-24 补充）

### 身份分级（B 站是公开环境，默认他人皆可能是恶意第三人）
- 主人私聊：可看到 BV 号、链接、视频名、分区等完整元数据（这是给主人看的，不是 B 站公开输出）
- B 站互动/公开输出：只谈当前相关话题，只表达看法和态度；**不透露以前看过什么、不引用记忆、不给任何来源线索**
- 客人/群聊：工具直接拒绝（不触发浏览），更拿不到任何 B 站记忆

### 互动原则
- 评论：只就当前视频的相关话题发表看法和态度，不引用历史记忆，不带链接/来源/个人信息
- 动态：需授权，内容不得暴露她的浏览历史或任何人的信息
- 私信：默认永久关闭；开关存在但需二次确认 + 明确理由，且永不主动发起

### 显式开关（命令 ↔ 设置界面双向同步）
- 三个开关：comment / dynamic / dm，存 settings_kv 单键 JSON（bili_interaction）
- 命令：『开启B站评论』→ 她回『确定开启评论？回复 确认 生效』→ 用户『确认』→ 写入 settings_kv
- 设置界面从同一 settings_kv 读取状态，命令改完 UI 立刻同步（刷新可见）
- 二次确认沿用项目已有 workspace.js 的 confirm=true 模式，不另起炉灶
- 默认全关；dm 即使开了也永不主动私信，只在被明确要求时才可能用
## 九、能力齐备性与互动扩展（2026-11-24 追加）

用户要求：接口可以不用，但不能没有。已实现的只读接口：
- 视频：热门 popular、搜索 search、字幕 subtitles、评论 comments、视频信息 videoInfo
- 文字专栏：opus（文章详情 + 内容摘要分析）
- 直播：liveInfo（直播间状态）、liveList（分区直播列表）
- 音乐：musicSearch（音乐区搜索）
- 扫码登录：qrGenerate / qrPoll / loginStatus / logout

互动能力（视频 + 专栏）：
- like 点赞、coin 投币、favorite 收藏、comment 评论（视频）
- opusLike / opusCoin / opusFavorite（专栏）
- 均需对应开关开启 + 登录；评论额外要求话题相关、禁引流/私信

六个显式开关：comment / dynamic / dm / like / coin / favorite（默认全关）。
命令（setInteraction，二次确认）与设置界面（/api/bili/interaction）读写同一 settings_kv 键，双向同步。
